# Making delivery safe with end-to-end idempotency keys

## Technique

Start from the assumption that **every hop can deliver more than once**, and stop
trying to buy exactly-once from any of them. Then make duplicates harmless by
giving each retry boundary a key, and letting one identity travel as far along the
path as it can:

| Hop | Key | Enforcement |
| :--- | :--- | :--- |
| Capture to ingestion | Client-generated UUID, minted **at capture** | Unique constraint on the ingestion table; insert with conflict-do-nothing |
| Ingestion to broker | The event's own id (in an outbox design, the outbox row id) | Published as the broker's message id, so the broker's dedup window drops duplicate publishes |
| Broker to consumer | The same event id | Consumer records processed ids durably and skips what it has seen |

The rule that generates the table, and the one worth remembering when the shape
differs: **the key must be generated by whoever retries, before the first
attempt, and must not change between attempts.** A client that retries has to mint
the key on the device; a relay that retries has to reuse the row id it already
has. A key generated by the receiver, or regenerated per attempt, is decoration.

That rule also explains why this is usually **two keys, not one**. The capture key
answers "is this the same submission the user made, arriving again?" The event id
answers "is this the same fact, delivered again?" They are different questions
with different retry domains — one client submission legitimately produces one
event, and conflating them means either the client controls your event identity or
your event identity cannot survive a client retry. Carry both, and document which
boundary each one guards.

**Where the first row's obligation is discharged.** This page owns the hops from
the ingestion commit onward — relay to broker, broker to consumer. The capture
key's own design (client-side minting, the unique constraint, the
`ON CONFLICT DO NOTHING` insert, and the append-only table it lands in) belongs
to `guidance-cqrs-projections/concepts/append-only-source-stream.md`; that page
is the other end of this chain, and the two are one decision seen from either
side of the ingestion boundary.

**Dedup must wrap the effect, not just the write.** Recording the id after an
upsert protects the row and does nothing for the notification, the webhook, the
external posting, or the counter increment that ran beside it. The idempotency
boundary has to enclose everything the message causes — ideally by making the
dedup record and the effect commit together.

**Scope the key.** A dedup key accepted from an untrusted client, checked
globally, is a write-suppression channel: submit a key someone else will use and
their write silently disappears. Scope uniqueness to the tenant or principal that
supplied it.

**Version the dedup scope if you intend to replay.** A consumer that dedups on
event id alone will correctly ignore a deliberate replay — which is exactly the
thing you replayed *for*. Key the consumer's dedup state on the event id **and**
the processing generation (a projector version, a rebuild id), so an intentional
rebuild is not swallowed by the machinery meant to absorb accidents.

## Applies when

- **Any hop can retry.** Mobile or field clients with store-and-forward queues,
  at-least-once brokers, HTTP clients and proxies that retry on timeout, relays
  that republish after a crash, or any stream you intend to replay. In practice
  this is every distributed path; the question is only whether the duplicates are
  currently visible.
- The effect of a duplicate is materially wrong rather than merely redundant — a
  doubled accounting entry, a second charge, a second notification to a human, a
  double-counted metric that feeds a decision.
- The retrying party can produce a stable identifier before its first attempt and
  carry it across restarts. A mobile client that mints the key at capture time and
  persists it in its upload queue satisfies this; one that generates a UUID inside
  the request-sending function does not.
- The receiving side has somewhere durable to record what it has processed — a
  unique index, a processed-ids table, or a broker-managed dedup window whose
  bounds you understand.
- Delivery guarantees are at-least-once by design, which is the normal case: the
  transactional-outbox and relay-to-broker designs in this pack both produce
  at-least-once on purpose, and this page is the other half of that bargain.

## Doesn't apply when

- **Every operation is naturally idempotent by construction.** A keyed upsert that
  assigns state (`SET status = 'closed' WHERE id = ?`), a set insertion, a
  last-writer-wins document replacement, a pure read. Applying it twice reaches
  the same state as applying it once. Explicit dedup machinery here adds a table,
  a retention policy, and a failure mode for no behavioural gain. Note the
  boundary carefully: **appends and increments are not naturally idempotent**, and
  a system whose writes are mostly upserts often has two or three appends hiding
  in it that are the entire reason this page exists.
- **The actual requirement is ordering.** Deduplication does not give you
  ordering, and stacking more dedup on an out-of-order stream will not converge.
  If the symptom is "events arrived in the wrong sequence and the projection is
  wrong," the tools are per-key sequence numbers with gap detection, version
  fields with optimistic concurrency, or a single-writer-per-key partition — not a
  dedup table. Diagnose which one you actually have before building either.
- **No party on the path can supply a stable key.** A third-party webhook with no
  event id, or a batch file with no per-record identity, leaves only
  content-based deduplication — hashing the payload — which cannot distinguish a
  retry from a genuinely repeated identical event. That is a different technique
  with a different, worse failure mode (silently merging distinct events), and it
  should be chosen knowingly.
- **Duplicates are cheap and detectable downstream.** A search index or a cache
  that will be overwritten by the next update, or an analytics sink that
  deduplicates at query time. Pushing the dedup to the place that already does it
  beats adding a second mechanism.
- **The effect is genuinely external and non-idempotent, and no key can be
  threaded to it.** A payment processor without an idempotency key parameter, a
  physical device actuation. Then the honest design is a durable
  intent-and-confirmation record with reconciliation, not a dedup table that
  claims a guarantee it cannot enforce past its own boundary.

## Trade-offs

Buys the ability to make every hop at-least-once — which is cheap, well-supported,
and what the infrastructure actually offers — while behaving as though the path
were exactly-once. That is the whole reason to do it: exactly-once delivery is
either unavailable or extremely expensive at every layer, and idempotent
processing converts it into a local, testable property of each receiver.

Costs a key on the wire **forever**. Once clients are in the field carrying a
capture key, that contract cannot be changed without a coordinated client
migration; the key's shape, its scope, and its generation point are locked in from
the first release. It also costs a unique index at ingestion (with the write
amplification and conflict handling that implies), durable dedup state at every
consumer, retention policies for that state, and a design review every single time
a hop is added to the path — because a new hop with no key is a new duplicate
source and nothing will announce it.

The subtler cost is that idempotency and replay pull in opposite directions.
Machinery that makes redelivery a no-op also makes deliberate reprocessing a
no-op unless the dedup scope is versioned. Teams discover this during their first
projection rebuild, when nothing happens and everything looks fine.

Quality attributes: this moves **integrity** and **availability** — retries become
safe, so any hop is free to retry aggressively rather than fail. It costs
**storage**, **write latency at the ingestion constraint**, and **evolvability of
the client contract**.

**What would make this stale.** Two futures. If idempotency keys become a
first-class primitive of the platforms on the path — standardized request headers
honoured by every intermediary, durable dedup managed by the runtime rather than
by each consumer's table — then most of this becomes configuration rather than
design, and the failure modes below shift from "we built it wrong" to "we
configured the bounds wrong." The other future is transactional processing that
genuinely spans producer and consumer, which would let some paths stop reasoning
about duplicates at all. Neither has arrived end-to-end; when either does for
your stack, re-derive which hops still need their own key.

## Failure modes

- **Dedup at one hop only.** The most common shape and the most misleading,
  because a dedup mechanism is visibly present. The broker's publisher-dedup
  window keys on the message id the publisher supplies; a client retry that
  produced a *second submission* upstream produces a *second, distinct* event with
  a *different* id, which the broker correctly treats as new. Two rows, two
  events, two accounting entries — with the dedup window doing exactly what it was
  configured to do. Every retry boundary needs its own key; a key at one boundary
  says nothing about any other.
- **Dedup windows sized shorter than the longest realistic retry gap.** Broker
  dedup windows commonly default to a couple of minutes. The retry gaps that
  matter are hours: a field client returning from a day without connectivity, a
  relay restarted after an incident, a queue drained after a long outage. Size the
  window from the actual retry policy of the slowest retrying party and then add
  margin — and treat the window as a latency optimization, with the consumer's
  durable dedup state as the real guarantee.
- **In-memory dedup state.** A seen-set in the consumer process that resets on
  every deploy. It passes every test, works for weeks, and double-writes on the
  first redelivery after a rollout — which is precisely when redeliveries are most
  likely, because the deploy interrupted in-flight acknowledgements.
- **The key is regenerated on retry.** The client mints a fresh UUID inside its
  send function rather than at capture, so each attempt is a new identity. The
  ingestion unique constraint never fires and the dedup table never registers a
  hit. That is the tell worth instrumenting: **a dedup mechanism with a
  permanently zero hit rate is not proof that there are no duplicates — it is
  the most likely symptom of a broken key.**
- **Idempotent write, non-idempotent side effect.** The row upserts cleanly; the
  push notification, webhook, or external posting fires a second time. Users see
  the duplicate the code was written to prevent, and the dedup table shows it
  working. Any effect outside the transaction that records the dedup key needs the
  key threaded into it too.
- **Unbounded dedup state.** Processed-id tables have the same growth problem as
  an outbox and rarely get the same attention. The retention floor is not
  convenience — it must exceed the maximum redelivery horizon, which includes
  broker retention, the longest client retry gap, and any replay you might
  deliberately run. Prune below that and you have quietly re-armed duplicates.
- **Replay swallowed by dedup.** A projection is rebuilt from history, the
  consumer recognizes every id, and nothing changes. The operator concludes the
  rebuild worked. This is the failure that looks most like success, and the fix —
  including a processing generation in the dedup key — has to be designed in
  before the first rebuild, not after it.
- **Key collision as a write-suppression attack.** Client-supplied keys checked
  globally let one principal suppress another's writes by guessing or reusing a
  key. Scope uniqueness per tenant or per principal, and never derive the key
  from anything guessable and shared.
- **A new hop added without a key.** A queue, a proxy with retries, an
  intermediate service inserted between two existing components. Each is a
  legitimate change nobody thinks to review for duplicate semantics, and the
  duplicates it introduces surface weeks later as an inexplicable double entry.
  The countermeasure is a written statement of the delivery guarantee at every
  hop, kept current, so adding a hop obviously requires updating it.
- **The unique constraint fails open.** Conflict-do-nothing returns success and
  the caller treats it as "created," or the constraint is added as a non-unique
  index during a migration and nobody notices. Test the duplicate path
  explicitly: submit the same key twice and assert one row and one effect.

## Alternatives considered

- **Exactly-once delivery from the transport** — wins essentially nowhere as a
  substitute, because what is sold under that name is at-least-once delivery plus
  deduplication with a bounded window, which is this technique with the bounds
  hidden. It genuinely wins when producer and consumer sit inside one
  transactional system that can commit reads, processing and writes atomically —
  a real and useful case, but one whose boundaries end where that system does.
- **Natural idempotency by construction (keyed upserts, state assignment)** —
  wins whenever the operation can be expressed as "make it so" rather than "add
  one." Cheapest possible answer, no extra state, and worth restructuring an
  operation to reach. Loses for appends, counters, and anything with an external
  side effect.
- **Content-hash deduplication** — wins when no party can supply a key, such as
  third-party feeds and batch imports. Loses because two genuinely distinct
  identical events are indistinguishable from a retry, so it silently drops real
  data in exactly the domains (repeated readings, repeated identical
  transactions) where that is most likely.
- **Server-assigned idempotency tokens** — the client requests a token, then
  submits with it. Wins for synchronous APIs where the client can afford a
  round trip before acting, and it avoids trusting client-generated keys. Loses
  on offline-capable capture paths, where the whole point is that the first
  network contact may be hours after the action.
- **An `Idempotency-Key` request header on a synchronous API** — the widely
  deployed HTTP convention: the server stores the key with the response and
  replays the stored response on repeat. Wins for request/response APIs,
  especially payments. Complements rather than replaces this page — it covers the
  client-to-ingestion hop only, and says nothing about anything downstream of the
  ingestion commit.
- **Sequence numbers with gap detection** — wins when the requirement is ordering
  or completeness ("did I miss anything?") rather than duplication. Loses as a
  duplicate defence on its own, and requires a single writer per sequence to
  mean anything.
- **Downstream reconciliation instead of prevention** — a periodic job that finds
  and merges duplicates. Wins for effects that genuinely cannot carry a key, and
  as a backstop that measures whether the keys are working. Loses as a primary
  mechanism, because it is eventually-correct at best and the window between
  duplication and repair is exactly when a human sees the wrong number.
